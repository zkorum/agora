# Agora redesign — short brief

Unify facilitator, participant, and onboarding layouts. Preserve familiar participation and keep branded pages focused on contributing.

## Design next

- **Navigation:** account bottom left; organizations separate; smooth participant/facilitator transitions.
- **Organizations:** members/permissions, ownership versus partners, localized logos/content, contact/documents.
- **Email:** configure, compose/test/send/history, consent/preferences/unsubscribe.
- **Login/profile:** one account; autogenerated public handle/username and optional public display name. Offer existing AT Protocol sign-in or provision an Agora-managed PDS behind the scenes. Preserve participation and return to the intended action after onboarding.
- **Integrations:** separate personal/organization API/MCP access from login.
- **Prioritizing:** facilitator-owned plural weighting, following the Facilitator Preference model. Show the chosen survey question(s)/Mapping source and the facilitator's default result clearly.

**Retain from current code:** AI seed suggestions, Polis imports/GitHub sync, languages/translation, embeds/sharing, and account/session controls. Keep inherited settings and permission differences explicit.

## Agreed publication and URLs

- **All or nothing:** projects start unlisted; publication exposes the whole project and all its activities. No activity-level unlisting. Only listed projects show “Listed”.
- **After activity creation:** offer link/QR sharing or project publication. **Publish live** for more participants: appear in Explore, indexing, and promotion. **Publish as archive** to showcase results: automatically close all activities and appear in Explore’s Past section.
- **Reopening:** allowed after archive publication, with an explicit warning that the activities are public. Make open/closed status clear on the participant project page.
- **Permanent link:** a secure random project URL exists by default, stays fixed, and always resolves to the same project.
- **Public slug:** choose an available slug when publishing. First assignment keeps the permanent link valid. Later changes warn that the old slug stops pointing to this project and can be reused by someone else.
- **Future:** project subdomains and self-hosting.

## Decisions to resolve

- **Naming:** does “How should we call you?” set the public display name, or is an additional internal name needed?
- **Private access:** define any genuinely restricted access separately from unlisted, link-accessible projects.
- **Plural:** separate from ballot method. For live Prioritizing, do sources update continuously or use a fixed snapshot, and can viewers switch from the facilitator's default? For QV, who configures weighting and how are results presented?
- **Reusing statements:** when importing from another activity, are statements independent copies or kept in sync? What happens if the original changes after voting starts?

Deliver mobile/desktop journeys with onboarding return, empty/error/closed states; distinguish existing from planned features.
