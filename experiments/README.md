# Experiments

Sandbox for designing and testing prompts before wiring a winning approach into the agora project, based on MLflow.
Code and data required to run MLflow experiments are grouped by initiatives folders (experiments sharing same data and goal).
An MLflow experiment consists of MLflow-stored datasets for which MLflow prompts are applied, with MLflow judges evaluating the quality of the output.
First step is to create and evaluate manually judges on small datasets.
Second step is to use the judges to evaluate much bigger datasets, allowing for a more robust and reproducible evaluation than done manually.

# Folder structure

Shared tooling (this MLflow server, the `uv` environment) lives at the
top level. Each distinct initiative gets its own subfolder under
`initiatives/` — e.g. `initiatives/seed-opinions/` — with its own `data/raw/`,
`data/processed/`, `runs/`, and `scripts/`, all logging into MLflow
experiments namespaced by initiative (e.g. seed-opinions uses `seed-opinions-per-item`). Don't
put initiative-specific code or data directly at this top level; create a
new subfolder under `initiatives/` instead.

Managed with `uv` (Python 3.13 — mlflow is not yet compatible with 3.14).

```
initiatives/<name>/
  data/
    raw/              # immutable source data, never edited in place
    processed/         # generated by prepare_data.py — gitignored, regeneratable
  scripts/
    setup/              # run once (or on config change) per experiment
      prepare_data.py
      create_datasets.py
      configure_judges.py
      create_label_schemas.py
      register_prompts.py
    generate.py         # the reusable, parameterized run script
    export_run.py       # CSV export of a past run
  runs/                 # optional local scratch output, gitignored
  exports/               # CSV exports for stakeholder review — gitignored, private by default
  <initiative>-description.md  # the experiment plan (motivation, criteria, phases)
```

# To start a new initiative

See worked example: `initiatives/seed-opinions/seed-opinions-description.md`.

Drop real-world source data in `data/raw/`. Prefer real data (exports,
existing records) over a hand-written eval set where possible — it surfaces
edge cases a hand-written set wouldn't. Never edit `data/raw/` files in
place; all cleaning happens in `prepare_data.py` and writes to
`data/processed/`.

**Default tiers** (flat row caps — the simple default):

| Tier     | Cap  | Purpose                                                  |
| -------- | ---- | -------------------------------------------------------- |
| `dummy`  | 5    | Fastest possible check that the pipeline runs end to end |
| `small`  | ≤20  | Quick smoke test of judges/prompt against real data      |
| `medium` | ≤50  | Working set for actual prompt/judge iteration            |
| `large`  | ≤100 | Broader validation before committing to a winner         |

These are flat caps on total row count. **If your experiment needs
coverage guarantees instead** (e.g. "at least one example from every
category," not just "N rows total"), use a different selection rule and
name it accordingly.

# To start a new MLflow experiment

## Step 1 — Setting up and calibrating judges on small datasets

**MLflow experiment name**: defaults to the initiative name. Set via
`EXPERIMENT_NAME` + `mlflow.set_experiment(...)` at the top of each setup
script below — not a dedicated script of its own.

**MLflow datasets** (`create_datasets.py`): import each tier's processed
jsonl (see tiers above) into MLflow as a Dataset, so it's browsable/selectable as a
unit in the UI's Datasets tab (Datasets and Traces are two different
mechanisms — see "Lessons learned" below).

**Judges** (`configure_judges.py`): define the scorers once, in a script
importable by both setup and the generate/eval scripts.

- Prefer a **built-in scorer** (`Fluency`, `Safety`, `ResponseLength`,
  `Guidelines`, etc. — see `mlflow.genai.scorers`) over writing your own
  whenever one already covers the criterion. `ResponseLength` in
  particular covers deterministic length/bounds checks — no LLM call
  needed.
- For criteria with no built-in match, use `mlflow.genai.judges.make_judge()`
  with natural-language instructions.
- **Keep every judge's output on one consistent scale.** Built-in scorers
  are hard-locked to `yes`/`no` (`mlflow.genai.judges.CategoricalRating`),
  so make custom `make_judge()` judges return `yes`/`no` too — mixed scales
  can't be compared or aggregated across judges.
- **`register()`ing a custom `@scorer`-decorated Python function fails
  outside Databricks** ("arbitrary code execution during deserialization"
  — a deliberate security boundary, not a bug). If you need it listed in
  the Scorers UI on a self-hosted server, it must be a built-in or a
  `make_judge()` instructions-judge; a raw `@scorer` function still works
  fine _inside_ `evaluate()`, it just won't register.
- **Model routing**: prefer the MLflow server's built-in AI Gateway
  (configured via the UI — Endpoints — with the provider API key stored
  server-side) over a direct provider URI needing a local
  `<PROVIDER>_API_KEY` env var. Reference it as `model="gateway:/<endpoint-name>"`.
  This keeps API keys out of every client shell.

**Manual/human evaluation** (if used) (`create_label_schemas.py`): create
one label schema per judge criterion you want humans to check, matching
that judge's `name` and `yes`/`no` scale so judge and human labels are
directly comparable and compatible with
`mlflow.genai.judges.AlignmentOptimizer.align()` later. The review queue
itself isn't a separate setup script — `generate.py` creates a queue named
after the run and attaches that run's traces to it automatically, but only
when at least one label schema exists (so experiments without a
human-review step don't get an empty queue). One queue per run keeps
different runs' items from mixing, so there's no need to clear anything
between runs.

**Prompt registry** (`register_prompts.py`): `mlflow.register_prompt(name=...,
template=[{"role": "system", "content": "..."}, {"role": "user", "content":
"..."}], commit_message="...")`. Template variables use `{{double_brace}}`
syntax; `prompt.format(**kwargs)` renders the whole chat-message list at
once.

> **Gotcha**: `register_prompt()` associates the prompt with whichever
> experiment is currently active — and defaults to the `Default`
> experiment (id `0`) if none is set. Always call `mlflow.set_experiment()`
> **before** `register_prompt()`, or the prompt won't show up when
> browsing your actual experiment.

### Dummy run

`scripts/generate.py`: reusable and parameterized — takes a prompt
name/version and a dataset tier (env vars or CLI args), not hardcoded to
one prompt variant. It should:

1. Load the specified prompt version from the registry.
2. For each row in the specified dataset tier, render the prompt and call
   the model (via the AI Gateway). Always trace.
3. Score the generated candidates with the configured judges
   (`mlflow.genai.evaluate()`), under a **descriptive run name** so runs
   stay distinguishable in the UI.
4. If human review is part of the loop, attach the freshly generated
   items to the review queue, marked for manual review.

Run it against the `dummy` (5-row) tier first. Check:

- All judges actually ran and returned scores (not silently errored/timed
  out — verify trace counts against the raw DB if in doubt, don't trust a
  printed "success" count alone; async trace export and unthrottled
  concurrency can both silently drop or stall work).
- Anything marked for manual review actually landed in the queue.

Iterate with the user until the dummy run's dimensions (row count, judges
run, review items created) look right before scaling up.

### Judge calibration (exit criterion for Step 1)

Before trusting a judge on bigger datasets, check it against human labels:

- Label **at least 30 generated items blind** (via the review queue, before
  looking at the judge's verdict). Below ~30, one or two disagreements swing
  the result too much to trust.
- Stratify the sample so each judge sees both clear-pass and clear-fail
  items — a random draw over-samples the easy majority. Hand-written
  adversarial fixtures (items designed to fail one specific judge) are a
  cheap way to cover the fail side.
- Compute agreement **per judge**, not overall. Poor agreement on one judge
  usually means its instructions are ambiguous: rewrite them (or use
  `AlignmentOptimizer.align()` on the collected human labels) and re-check
  before moving on.

Only judges that pass calibration go into Step 2.

## Step 2 — Prompt iteration and evaluation at scale

Goal: use the calibrated judges to iterate on prompt/model variants, then
compare the best ones on a dataset too large to review by hand and pick a
winner.

### Prompt iteration

Iterative loop, one exchange at a time with the user:

- Run `generate.py` against a real tier (`small`/`medium`) with a new
  prompt version or model. Give every run a unique, readable name.
  _Seed-opinions example:_ the run name always gets a UTC timestamp
  appended, so consecutive runs never overwrite each other in the UI, and
  `SEED_OPINIONS_RUN_LABEL` sets a readable prefix (e.g. `few-shot-v2`)
  instead of the default `<prompt-name>_v<version>_<tier>`.
- Review the outputs and judge verdicts, then decide the next variant with
  the user.
- If a judge needs changing along the way, re-run Step 1's calibration for
  it before trusting its scores again.

Once a few variants look promising, move to the larger comparison below.

### Comparison at scale

**Scale the data.** Use the `large` tier (or a bigger one). Aim for
**at least 50 real inputs**: below that, one unusual input can decide which
variant "wins". Grow the Dataset when a judge criterion has too few
examples to discriminate (e.g. almost every item passes).

**Freeze the judges during a comparison.** Every variant being compared
must be scored by the same judge versions on the same Dataset. If a judge
changes mid-comparison, re-run the earlier variants too, or their scores
aren't comparable.

**Run each variant.** One `generate.py` run per prompt version × model,
same tier, with a readable run label. Compare the runs in the MLflow UI:

- Pass rate **per judge**, not one averaged score — a variant that gains on
  brevity but loses on safety isn't a winner.
- Latency and cost per item (from the traces), when they matter for the
  production decision.

**Operational care.** Large runs are where the lessons below bite: keep
`evaluate()` concurrency throttled, and check trace/assessment counts
against `mlflow.db` rather than trusting the printed totals. Estimate the
call count first: rows × (1 generation + number of LLM judges).

**Human spot-check before trusting the result.** Review **at least 20 items
or ~20% of the run, whichever is larger**, sampled across the score
distribution: high-scoring, low-scoring, borderline, and items where judges
disagree with each other. If humans disagree with a judge on a meaningful
share of items, go back to Step 1 calibration for that judge.

**Freeze the winner.**

- Point an alias at the winning prompt version
  (`mlflow.set_prompt_alias(name=..., alias="production", version=...)`) so
  downstream code and later runs reference the alias, not a version number.
- Keep the winning run's Dataset + outputs as a **golden regression set**:
  future prompt edits run against it first, instead of re-running the whole
  comparison.
- Record the decision (variant, run IDs, key per-judge numbers) in the
  initiative's `<initiative>-description.md`.

# Exporting results for stakeholder review (optional)

Export a run to CSV, at any step. In-process, straight from `evaluate()`:

```python
result = mlflow.genai.evaluate(data=data, scorers=scorers)
result.result_df.to_csv(f"exports/{run_name}.csv", index=False)
```

`result_df` is only available in-process from the `evaluate()` call
itself. To export a past run, rebuild the same table from
`mlflow.search_traces(run_id=...)` and each trace's
inputs/outputs/assessments — see `initiatives/seed-opinions/scripts/export_run.py`,
which also includes human review labels next to the judges' verdicts.

**Treat every export as private by default.** If the underlying data
includes real user-submitted content (conversation titles/bodies,
opinions) that isn't already public, the CSV must never be committed:

- Write it to `exports/` under the initiative folder — gitignored (see
  folder structure above), same convention as `data/raw/` and `runs/`.
- Share it through a channel appropriate to the data's actual sensitivity
  (a private message/drive with the right audience, not a public link or
  anything pasted somewhere public). Gitignoring the file keeps it out of
  git; it does nothing to make the file itself safe to hand off carelessly
  — that's a separate judgment call about the data, every time.

# Lessons learned (apply generally, not just to seed-opinions)

- **Verify against the raw store, not printed output.** A script can print
  "logged 14,652 traces" while the server actually persisted 857 of them
  (async export queue overflow, no error raised). When a number matters,
  check `sqlite3 mlflow.db "select count(*) from ..."` or an equivalent
  direct query.
- **Throttle `evaluate()` concurrency.** Defaults to `MLFLOW_GENAI_EVAL_MAX_WORKERS=10`
  × `MLFLOW_GENAI_EVAL_MAX_SCORER_WORKERS=10` — up to ~100 concurrent model
  calls, easily enough to exhaust a normal API rate limit and stall
  silently (no error, no further progress, no retries visible). Set both
  low (e.g. `2`) for anything beyond a trivial row count.
- **Tags vs. inputs vs. expectations**: `inputs` is what the judge/model
  actually needs to see (title, body, sibling context). `tags` is for
  filterable/searchable per-record metadata (language, source id,
  conversation id) — trace-level `attributes` is a fixed system schema,
  not a place for custom data. `expectations` is for ground-truth/target
  values a judge might compare against, not a place to stash the item
  under test — that's `outputs`.
- **MLflow Datasets vs. Traces are two different mechanisms.** Datasets
  (`mlflow.genai.datasets`) are a tabular store you build with
  `create_dataset()`/`merge_records()`. Traces are individual execution
  records, browsable/filterable/selectable in the UI, with a native
  "select rows → Add to evaluation dataset" action that Datasets alone
  don't have. Always use both.

# MLflow tracking server

Start the server (SQLite backend store, local filesystem artifact store):

```bash
cd experiments
uv run mlflow server \
  --backend-store-uri sqlite:///mlflow.db \
  --default-artifact-root ./mlruns \
  --host 127.0.0.1 \
  --port 5001
```

Then open http://127.0.0.1:5001

Notes:

- Port `5001` is used instead of MLflow's default `5000` because macOS's AirPlay
  Receiver (ControlCenter) listens on `5000` by default, causing a bind conflict.
- `mlflow.db` and `mlruns/` are gitignored — local scratch state only.
  Anything that must outlive this machine (the retained prompt, the
  judges) is kept as a copy in the initiative's setup scripts, and the
  key results in its `<initiative>-description.md`.

# Logging runs

Point experiment scripts at the server via:

```bash
export MLFLOW_TRACKING_URI=http://127.0.0.1:5001
```

Then use `mlflow.set_experiment(...)`, `mlflow.start_run()`, `mlflow.log_param()` /
`mlflow.log_metric()` from any script run with `uv run python ...` in this folder.
